# Smart Logistics — Data Engineering & ML

Проект аналитической платформы для обработки данных о стоимости грузоперевозок. Реализованы OLTP-хранилище, ETL-процессы на Apache Airflow, многослойное DWH, контроль качества данных, аналитические витрины и ML-модель прогнозирования стоимости перевозок.

Проект построен на синтетических данных и предназначен для демонстрации практических навыков Data Engineering, DWH и Machine Learning.

## Источники данных

OLTP PostgreSQL содержит синтетические данные, имитирующие информационную систему логистической компании.

Основные таблицы:

| Таблица             | Назначение                                |
| ------------------- | ----------------------------------------- |
| `prices`            | Цены и характеристики грузоперевозок      |
| `cities`            | Справочник городов                        |
| `body_types`        | Типы кузовов и стандартизированные группы |
| `price_body_types`  | Связь цен с типами кузовов                |
| `exchange_rates`    | История валютных курсов                   |
| `price_dates`       | Даты, связанные с ценами                  |
| `price_group_stats` | Агрегированная статистика цен             |

Для таблицы `prices` предусмотрена генерация приблизительно 300 000 синтетических записей.

Данные содержат информацию о маршрутах, расстоянии, весе, объёме груза, валюте, стоимости перевозки, типах кузовов и организациях.

## ETL Pipeline

ETL реализован на Apache Airflow.

### RAW

RAW предназначен для сохранения исходных данных с возможностью восстановления состояния источника на момент конкретной загрузки.

Основная структура RAW:

```sql
source_id   BIGINT,
payload     JSONB,
batch_id    UUID,
extracted_at TIMESTAMPTZ
```

История загрузок идентифицируется через `batch_id`.

Для каждой исходной записи сохраняется отдельная версия в рамках batch.

Дополнительно используются таблицы:

- `raw.etl_batches` — история выполнения ETL.
- `raw.etl_watermarks` — контрольные точки инкрементальной загрузки.

Основные этапы:

1. Export — выгрузка данных из OLTP.
2. Transform — приведение данных к унифицированной JSONL-структуре.
3. Load — пакетная загрузка в PostgreSQL через COPY.

Между задачами передаются пути к промежуточным файлам через XCom, а не сами наборы данных.

Для таблицы `prices` применяется инкрементальная выгрузка по `updated_at` с временным перекрытием для снижения риска пропуска изменений.

### CORE

CORE содержит стандартизированные измерения, факты и связи между сущностями.

**Измерения:**

| Таблица                     | Назначение                           |
| --------------------------- | ------------------------------------ |
| `core.dim_city`             | Канонический справочник городов      |
| `core.map_source_city`      | Сопоставление исходных ID городов    |
| `core.dim_body_group`       | Стандартизированные группы кузовов   |
| `core.map_source_body_type` | Сопоставление исходных типов кузовов |

Для городов используется surrogate key `city_id`.

Поскольку `gc_id` не уникален в OLTP, несколько исходных записей одного города сопоставляются с одной канонической записью через `map_source_city`.

Аналогичный подход применяется к типам кузовов: несколько исходных типов могут относиться к одной группе `std_id`.

**Факты и связи:**

| Таблица                        | Назначение                   |
| ------------------------------ | ---------------------------- |
| `core.fact_prices`             | Факты стоимости перевозок    |
| `core.bridge_price_body_group` | Связь цен с группами кузовов |

В `fact_prices` сохраняются основные характеристики перевозки:

- маршрут;
- дата загрузки;
- расстояние;
- вес и объём;
- исходная цена;
- валюта;
- цена в рублях;
- категория веса и объёма;
- идентификатор организации.

`bridge_price_body_group` обеспечивает связь «многие ко многим»: одна цена может относиться к нескольким стандартизированным группам кузовов.

Для расчёта цены в рублях используется точное сопоставление валютного курса по коду валюты и дате `nearest_rate_date`.

### MART

В MART реализованы две аналитические таблицы:

**`mart.mart_route_card`**

Агрегированная аналитика стоимости перевозок с гранулярностью:

```text
Месяц
  + Город отправления
  + Город назначения
  + Группа кузова
  + Категория веса
```

Основные показатели:

| Поле               | Назначение                                    |
| ------------------ | --------------------------------------------- |
| `deals_count`      | Количество ценовых записей                    |
| `carriers_count`   | Количество уникальных организаций             |
| `avg_price_rub`    | Средняя стоимость                             |
| `p25_price_rub`    | 25-й перцентиль                               |
| `median_price_rub` | Медианная стоимость                           |
| `p75_price_rub`    | 75-й перцентиль                               |
| `avg_km_price`     | Средняя стоимость километра                   |
| `cv_price`         | Коэффициент вариации                          |
| `mom_change_pct`   | Изменение к предыдущему месяцу                |
| `yoy_change_pct`   | Изменение к аналогичному месяцу прошлого года |
| `reliability`      | Оценка надёжности агрегата                    |

В качестве идентификатора перевозчика используется `organization_id`.

Для MoM и YoY применяются сравнения с соответствующими календарными периодами.

**`mart.ml_price_predictions`**

Предназначена для хранения результатов ML-прогнозирования:

- прогнозная стоимость;
- фактическая стоимость;
- абсолютная ошибка;
- относительная ошибка APE;
- тип выборки;
- версия модели.

Уникальность прогнозов обеспечивается комбинацией `price_id` и `model_version`.

## Data Quality

Для контроля качества данных предусмотрен отдельный механизм DQ.

Невалидные цены не загружаются в `core.fact_prices`, а сохраняются в:

```text
core.dq_quarantine_prices
```

Таблица содержит:

- исходный ID цены;
- исходный JSONB payload;
- код причины отклонения;
- описание ошибки;
- batch загрузки;
- дату помещения в карантин.

Основные правила проверки:

| Проверка      | Правило                            |
| ------------- | ---------------------------------- |
| Цена          | Должна быть больше нуля            |
| Расстояние    | Должно быть больше нуля            |
| Вес           | Не может быть отрицательным        |
| Объём         | Не может быть отрицательным        |
| Города        | Должны быть сопоставлены с Core    |
| Валютный курс | Должен существовать на точную дату |
| Валютный курс | Должен быть больше нуля            |

Загрузка в карантин защищена уникальным индексом по `source_price_id`, `batch_id` и `reason_code`, что предотвращает повторное создание одинаковых записей при повторном запуске ETL.

## Machine Learning

Для прогнозирования стоимости грузоперевозок реализован отдельный ML Pipeline.

### Постановка задачи

Тип задачи — регрессия.

Целевая переменная:

```text
target_price_rub = price_rub
```

Прогнозируется стоимость перевозки в рублях по характеристикам маршрута, груза и условиям перевозки.

### Подготовка датасета

Для первой версии модели использовались записи, удовлетворяющие условиям:

```sql
is_fact = TRUE
AND outlier_mark = FALSE
AND loading_date <= DATE '2026-11-08'
AND price_rub > 0
AND distance > 0
```

Количество наблюдений:

| Выборка    |  Количество |
| ---------- | ----------: |
| Train      |     169 011 |
| Validation |      36 043 |
| Test       |      36 064 |
| **Всего**  | **241 118** |

Разделение выполняется хронологически, без случайного перемешивания:

| Выборка    | Период                  |
| ---------- | ----------------------- |
| Train      | 03.10.2023 — 22.03.2026 |
| Validation | 23.03.2026 — 02.08.2026 |
| Test       | 03.08.2026 — 08.11.2026 |

Записи одного дня не разделяются между разными выборками.

Датасеты сохраняются в формате Parquet.

### Признаки модели

**Числовые:**

- расстояние;
- общий вес;
- общий объём;
- год загрузки.

**Категориальные:**

- город отправления;
- город назначения;
- категория веса;
- категория объёма;
- первая группа кузова;
- вторая группа кузова;
- месяц загрузки;
- день недели;
- тип цены;
- признак комплексной перевозки.

При нескольких группах кузовов они преобразуются в два отдельных признака. Это позволяет сохранить одну запись на одну перевозку, не размножая наблюдения при JOIN.

Перед обучением целевая переменная логарифмируется:

```python
y = np.log1p(price_rub)
```

### Обучение

Используемые модели:

- `DummyRegressor` — базовая модель для сравнения;
- `CatBoostRegressor` — основная регрессионная модель.

Для CatBoost применены:

| Параметр       |        Значение |
| -------------- | --------------: |
| Iterations     | 2000 (максимум) |
| Best iteration |             524 |
| Depth          |               8 |
| Learning rate  |            0.05 |
| Random seed    |              42 |
| Loss function  |            RMSE |

Для подбора количества итераций используется Validation и механизм Early Stopping.

Финальная модель обучается на Train + Validation, а Test используется только для итоговой оценки.

### Оценка качества

Метрики рассчитываются после обратного преобразования прогнозов в рубли.

| Метрика | DummyRegressor |     CatBoost |
| ------- | -------------: | -----------: |
| MAE     |      120 894 ₽ | **25 820 ₽** |
| RMSE    |      206 337 ₽ | **57 184 ₽** |
| MAPE    |         83.40% |   **13.61%** |
| WAPE    |         63.58% |   **13.58%** |
| R²      |         -0.178 |   **0.9095** |

CatBoost снизил MAE примерно на 78.6% относительно baseline.

Качество на Validation и Test:

| Метрика | Validation |     Test |
| ------- | ---------: | -------: |
| MAE     |   25 028 ₽ | 25 820 ₽ |
| RMSE    |   60 996 ₽ | 57 184 ₽ |
| MAPE    |     13.79% |   13.61% |
| R²      |     0.8818 |   0.9095 |

Результаты показывают стабильное качество модели на отложенном временном периоде.

**Важно:** данные проекта синтетические. Полученные метрики характеризуют качество модели на закономерностях генерации этих данных и не являются оценкой точности прогнозирования на реальном рынке грузоперевозок.

## Запуск проекта

### Требования

- Docker
- Docker Compose
- Git

Для локальной разработки дополнительно понадобится Python 3.10+.

### 1. Клонирование репозитория

```bash
git clone <REPOSITORY_URL>
cd smart-logistics
```

### 2. Настройка переменных окружения

Создать `.env` на основе `.env.example` и заполнить параметры подключения к PostgreSQL и Airflow.

```bash
cp .env.example .env
```

Не добавлять `.env` с реальными паролями и секретами в Git.

### 3. Запуск инфраструктуры

```bash
docker compose up -d
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

### 4. Airflow

Веб-интерфейс Airflow:

```text
http://localhost:8080
```

Доступ к OLTP и DWH также можно настроить через DBeaver, используя опубликованные Docker-порты.

В Airflow используются подключения:

```text
oltp_postgres
dwh_postgres
```

### 5. Запуск ETL

DAG выполняют выгрузку исходных таблиц из OLTP в RAW, а затем загрузку стандартизированных данных в Core.

Порядок загрузки:

1. RAW — города, типы кузовов, курсы валют, цены и связи цен с типами кузовов.
2. CORE — города и группы кузовов.
3. CORE — факты цен.
4. CORE — bridge связей цен с группами кузовов.
5. MART — агрегированная аналитика маршрутов.

Перед запуском зависимых задач необходимо убедиться, что соответствующие справочники и исходные RAW-данные уже загружены.

### 6. Подготовка ML-датасета

Подготовка выполняется модулем `ml.dataset`.

```bash
python -m ml.train
```

Команда выше запускает обучение на ранее сформированных Parquet-выборках.

Для подготовки датасета используется отдельная Airflow-задача `ml_dataset_prepare`.

### 7. Обучение модели

```bash
python -m ml.train
```

В результате создаются модель CatBoost, метрики и тестовые прогнозы.

### 8. Сохранение прогнозов в Mart

Для загрузки прогнозов предусмотрен модуль:

```bash
python -m ml.persist_predictions
```

Перед запуском необходимо убедиться, что модель и файл тестовых прогнозов созданы, а таблица `mart.ml_price_predictions` существует.
